# 0015. 사람 탐지는 VisDrone YOLOv8m, 추적은 PointTracker

- 상태: 채택(라이선스는 팀 안의 시연·학습 목적으로 쓰는 동안만 해당하고, 배포하거나 저장소·가중치를 공개하기 전에 다시 확인한다. 아래 '열린 질문' 1)
- 기록: 2026-10-20
- 관련: 0001(대체됨), overview.md '기술 스택·외부 연동 사양 > 분석 모델', 알려진 한계 16~18, conventions.md `DETECTOR / DETECT_CONF / DETECT_IMGSZ / YOLO_WEIGHTS / DETECT_DEDUPE_OVERLAP`, features/analyzer.md FNC-S-003

## 맥락
0001은 YOLO-CROWD(머리 탐지)와 ByteTrack으로 시작하되 실제 영상으로 다시 재서 확정하기로 했다. 가중치를 입수해 실제 영상과 새 표본으로 재 보니 아래 문제가 확인됐다.
- YOLO-CROWD는 정수리만 보이는 부감 영상에서 사람을 크게 놓친다(사람이 40명 넘게 보이는 장면에서 2명).
- 머리 박스가 작아 프레임 사이에 겹치지 않아 ByteTrack으로는 추적 번호가 거의 이어지지 않았다(번호가 붙은 박스 1~2%). #4 유입/유출·#5 체류 시간이 이 번호에 의존한다.

FNC-S-003의 상관계수 0.7 기준은 YOLO-CROWD도 새 표본에서 0.78로 만족한다. 그러므로 교체 이유는 기준 미달이 아니라 센 수의 비율(실제의 23%), 부감 영상에서의 누락, 추적 번호 유지다.

## 결정
- 탐지: VisDrone YOLOv8m(Ultralytics, 위에서 내려다본 사람 몸 박스). pedestrian·people 두 클래스를 사람 하나로 합친다. 입력 960, 신뢰도 0.3, NMS IoU 0.45, 같은 사람을 둘로 센 박스를 합치는 기능은 기본으로 끈다(`DETECT_DEDUPE_OVERLAP` 0). 합쳐서 얻는 이득(정밀도 등)은 아직 재지 않았고, 확인되면 그때 켠다.
- 추적: PointTracker. 박스가 겹치는지가 아니라 중심점 거리로 같은 사람을 잇는다(프로토타입 SkyCrowd에서 쓰던 방식을 다시 구현). 번호는 두 번 관측되면 부여한다.
- YOLO-CROWD는 `DETECTOR=yolo-crowd`로 계속 고를 수 있게 코드에 남긴다.
- 분석 프레임 수(`ANALYZE_FPS`)와 입력 크기는 바꾸지 않았다. 서버(VM)에 올려 느리면 그때 조정한다(PM 안내(2026-10-20): 서버 속도는 엄격하게 재지 않아도 된다).

## 영향
- 센 수는 여전히 실제의 일부(사진 기준 약 60~65%)다. '추정 인원'과 상대 혼잡 지표로만 쓰고 혼잡 단계 경계 밀도는 이 센 값 기준으로 실제 영상에서 맞춘다(알려진 한계 16).
- 박스가 사람 몸 전체가 된다(이전엔 머리). 좌표 파일 형식(x,y 왼쪽 위, 0~1)은 그대로다.
- 번호는 두 번째로 보인 프레임부터 붙는다. 영상 첫 프레임과 막 나타난 사람은 번호가 없고, 체류 시간은 처음 번호를 받은 프레임부터 잰다(초당 5프레임에서 0.2초 짧음). 번호를 세 번째부터 주면 가장자리로 들어오는 사람이 번호를 받기 전에 안쪽 띠로 옮겨 가서 유입을 놓쳤다.
- 같은 사람을 둘로 센 박스를 합치는 기능은 기본으로 끈다(`DETECT_DEDUPE_OVERLAP=0`). 켜면 밀집 장면에서 서로 다른 두 사람도 하나로 합칠 수 있고(사진에서 재현율 53% → 50%, 센 수/실제 0.65 → 0.60), 지금 문서에는 이득을 보여 주는 수치가 없다. 같은 120장으로 합치기를 켰을 때 정밀도 등 이득이 확인되면 그때 켠다.
- 추적 번호 비율은 번호의 정확도가 아니다(번호가 자주 바뀌어도 높게 나온다). PM 영상 8개로 분석에서 유입/유출·체류 시간까지 전체 흐름을 돌려 방향 분포가 장면(횡단보도 방향)과 맞는지 확인했다(정답 수는 없고, 카메라가 완전한 고정이 아니라 조금 움직인다). 사람이 센 값과의 비교는 아래 '사람이 센 값과 비교'에서 영상 7장으로 했다(세는 사람이 Claude라 팀원 검수 전).

## 열린 질문 (PM 확인 필요)
1. **라이선스**(정리됨): Ultralytics YOLOv8은 AGPL-3.0이고, 가중치(`mshamrai/yolov8m-visdrone`, SHA-256 `C1A19706FE83E8282795FB6C6CEC6A5E2A6E515C9B5FE4F558863D987EE24F8B`, 52,006,688바이트)와 학습 데이터(VisDrone, 연구 목적 공개)의 상업적 이용 여부는 확인하지 못했다. 그래서 가중치를 white-eyes-assets에 올리지 않았다. PM 결정(2026-10-20, 0001과 같은 방침): 현재는 팀 안의 시연·학습 목적으로 쓴다. 배포하거나 저장소·가중치를 공개하기 전에 가중치·데이터·Ultralytics 라이선스를 다시 확인한다.
2. **서버 속도**(정리됨): 입력 960은 이 PC에서 프레임당 약 0.5초라 `ANALYZE_FPS` 5(프레임당 0.2초)를 못 맞춘다. 더미 영상은 미리 분석해 캐시하니 준비 시간이 길어질 뿐이다(10분 영상, 초당 5프레임이면 약 25분). PM 안내(2026-10-20): 서버 속도는 엄격하게 재지 않아도 된다. 서버(VM 4 vCPU)에 올려 느리면 `ANALYZE_FPS`(2~3)나 `DETECT_IMGSZ`(640)로 낮춘다.
3. 라이브 캠이 늘면 공유 탐지기의 잠금 때문에 처리량이 합산된다(캠별 최신 프레임만 유지하는 큐 등은 라이브 구현 때 정한다).

## 사람이 센 값과 비교 (2026-10-21, 이슈 #38)
FNC-S-003 검수 기준 "실제 더미 영상 몇 개에서 사람이 센 값과 비교해 오차(상관계수, 실제 대비 비율)를 기록"에 따라 PM 영상 프레임을 골라 정답을 만들고, 기본 설정(VisDrone YOLOv8m 960, 신뢰도 0.3, 합치기 끔)의 센 값과 비교했다.

**표본**: 군중이 너무 빽빽한 영상 4개(1192335759, 1631905650, 1687922946, 475338200)를 뺀 `drone-vids-v1` 9개에서 영상마다 프레임 1장을 뽑았다. 시각은 시드 20261021(`random.Random(20261021)`)로 영상 앞뒤 1초를 뺀 구간에서 정했다. 프레임은 영상 원본 그대로(768×432)이고 저장소에는 올리지 않는다.

**정답을 센 방법과 한계 (중요)**: 세는 사람은 팀원이 아니라 Claude다. 프레임을 4조각(조각 경계 24픽셀 겹침)으로 나눠 3배 확대한 이미지를 육안으로 보며, 모델 값은 보지 않은 채 셌다. 사람으로 알아볼 수 있으면 세고(일부가 가려져도) 알아볼 수 없으면 세지 않았다. 조각 경계 안쪽 사람만 그 조각에서 셌고, 사람이 빽빽한 조각은 줄 단위로 어림했다. 그래서 값마다 오차를 함께 적는다(±10~25%). 이 값은 '사람이 직접 센 값'이 아니므로 팀원 검수 전의 값이다. 팀원이 클릭 세기 도구(`count.html`, 저장소 밖)로 검수해 값을 바꿀 수 있다.
