# 0015. 사람 탐지는 VisDrone YOLOv8m, 추적은 PointTracker

- 상태: 채택(단, 아래 '열린 질문'의 라이선스는 확인 전)
- 기록: 2026-10-20
- 관련: 0001(대체됨), overview.md '기술 스택·외부 연동 사양 > 분석 모델', 알려진 한계 16~18, conventions.md `DETECTOR / DETECT_CONF / DETECT_IMGSZ / YOLO_WEIGHTS / DETECT_DEDUPE_OVERLAP`, features/analyzer.md FNC-S-003

## 맥락
0001은 YOLO-CROWD(머리 탐지)와 ByteTrack으로 시작하되 실제 영상으로 다시 재서 확정하기로 했다. 가중치를 입수해 실제 영상과 새 표본으로 재 보니 아래 문제가 확인됐다.
- YOLO-CROWD는 정수리만 보이는 부감 영상에서 사람을 크게 놓친다(사람이 40명 넘게 보이는 장면에서 2명).
- 머리 박스가 작아 프레임 사이에 겹치지 않아 ByteTrack으로는 추적 번호가 거의 이어지지 않았다(번호가 붙은 박스 1~2%). #4 유입/유출·#5 체류 시간이 이 번호에 의존한다.

## 결정
- 탐지: VisDrone YOLOv8m(Ultralytics, 위에서 내려다본 사람 몸 박스). pedestrian·people 두 클래스를 사람 하나로 합친다. 입력 960, 신뢰도 0.3, NMS IoU 0.45, 같은 사람을 둘로 센 박스는 합친다(`DETECT_DEDUPE_OVERLAP` 0.25).
- 추적: PointTracker. 박스가 겹치는지가 아니라 중심점 거리로 같은 사람을 잇는다(프로토타입 SkyCrowd에서 쓰던 방식을 다시 구현). 번호는 두 번 관측되면 부여한다.
- YOLO-CROWD는 `DETECTOR=yolo-crowd`로 계속 고를 수 있게 코드에 남긴다.
- 분석 프레임 수(`ANALYZE_FPS`)와 입력 크기는 바꾸지 않았다. 서버(VM)에 올려 느리면 그때 조정한다(PM 안내(2026-10-20): 서버 속도는 엄격하게 재지 않아도 된다).

## 근거 (2026-10-20 재측정)
표본: VisDrone2019-DET **val** 분할에서 시드 20261020으로 무작위 120장(`random.Random(20261020).sample`, 파일 이름순 정렬), 사람 3,263명(pedestrian·people, 무시 영역 제외). 원본 사진은 저장소에 올리지 않는다. 데이터: `VisDrone2019-DET-val.zip` 81,638,851바이트, SHA-256 `ABEEA063037E5D20398837DEB11084E652402A34DDF4F207BDF541A6F2A35EF9`(공식 배포 파일, 받은 경로는 기록하지 못함). 측정은 이 PC(Intel i7-4790, CPU)에서 했다.

**영상**: PM이 준 `drone-vids-v1`(768×432, 위에서 내려다본 13개, 출처·라이선스 미확인) 중 사람이 개별로 보이는 8개를 10초씩(초당 5프레임) 돌렸다. 영상에는 정답이 없어서 장면을 눈으로 확인하고 모델끼리 비교했다.

| 설정 | 평균 인원 | 번호 있는 박스 | 평균 추적 길이 | 프레임당 |
|---|---|---|---|---|
| YOLO-CROWD 960 + PointTracker | 64명 | 66% | 8프레임 | 406ms |
| VisDrone YOLOv8m 640 + PointTracker | 97명 | 86% | 17프레임 | 299ms |
| VisDrone YOLOv8m 960 + PointTracker | 97명 | 85% (구현 PR의 두 번째 프레임 규칙으로는 86~96%) | 16프레임 | 554ms |

- 이 영상에서는 입력 640과 960의 인원·추적이 거의 같았다(영상 해상도가 작아서). 먼 곳의 작은 사람이 많은 사진에서는 960이 확실히 더 찾는다(재현율 39% → 53%).
- 같은 구성에서 ByteTrack은 광장·해변 영상에서 번호 있는 박스가 1~2%였다.
- 수천 명이 빽빽한 군중 영상(PM 영상 13개 중 4개)은 어느 모델도 개수를 못 맞췄다(실제 수천 명에 수십~300명). YOLO-CROWD의 300은 vendor NMS의 `max_det=300` 상한이다.
- 설정 후보 중 960을 고른 이유: 놓치는 사람이 적고(사진 재현율 53%), 이 서비스는 놓치지 않는 쪽이 중요하다. 속도는 입력 크기와 `ANALYZE_FPS`로 조정한다.

## 영향
- 센 수는 여전히 실제의 일부(사진 기준 약 60~65%)다. '추정 인원'과 상대 혼잡 지표로만 쓰고 혼잡 단계 경계 밀도는 이 센 값 기준으로 실제 영상에서 맞춘다(알려진 한계 16).
- 박스가 사람 몸 전체가 된다(이전엔 머리). 좌표 파일 형식(x,y 왼쪽 위, 0~1)은 그대로다.
- 번호는 두 번째로 보인 프레임부터 붙는다. 영상 첫 프레임과 막 나타난 사람은 번호가 없고, 체류 시간은 처음 번호를 받은 프레임부터 잰다(초당 5프레임에서 0.2초 짧음). 번호를 세 번째부터 주면 가장자리로 들어오는 사람이 번호를 받기 전에 안쪽 띠로 옮겨 가서 유입을 놓쳤다.
- 같은 사람을 둘로 센 박스를 합치는 규칙은 밀집 장면에서 서로 다른 두 사람도 하나로 합칠 수 있다(사진에서 재현율 53% → 50%). `DETECT_DEDUPE_OVERLAP=0`으로 끌 수 있다.
- 추적 번호 비율은 번호의 정확도가 아니다(번호가 자주 바뀌어도 높게 나온다). PM 영상 8개로 분석에서 유입/유출·체류 시간까지 전체 흐름을 돌려 방향 분포가 장면(횡단보도 방향)과 맞는지 확인했다(정답 수는 없고, 카메라가 완전한 고정이 아니라 조금 움직인다). 사람이 직접 센 값과의 비교는 아직 하지 않았다.

## 열린 질문 (PM 확인 필요)
1. **라이선스**: Ultralytics YOLOv8은 AGPL-3.0이고, 가중치(`mshamrai/yolov8m-visdrone`, SHA-256 `C1A19706FE83E8282795FB6C6CEC6A5E2A6E515C9B5FE4F558863D987EE24F8B`, 52,006,688바이트)와 학습 데이터(VisDrone, 연구 목적 공개)의 상업적 이용 여부는 확인하지 못했다. 그래서 가중치를 white-eyes-assets에 올리지 않았다. 팀 안의 시연·학습 목적이면 지금처럼 써도 되는지, 배포 전에 어떤 확인이 필요한지 정해 달라.
2. **서버 속도**(정리됨): 입력 960은 이 PC에서 프레임당 약 0.5초라 `ANALYZE_FPS` 5(프레임당 0.2초)를 못 맞춘다. 더미 영상은 미리 분석해 캐시하니 준비 시간이 길어질 뿐이다(10분 영상, 초당 5프레임이면 약 25분). PM 안내(2026-10-20): 서버 속도는 엄격하게 재지 않아도 된다. 서버(VM 4 vCPU)에 올려 느리면 `ANALYZE_FPS`(2~3)나 `DETECT_IMGSZ`(640)로 낮춘다.
3. 라이브 캠이 늘면 공유 탐지기의 잠금 때문에 처리량이 합산된다(캠별 최신 프레임만 유지하는 큐 등은 라이브 구현 때 정한다).
